## 1) Ordem das aulas: array nunca ordenado

`classLessons` ([main.jsx:3077](src/main.jsx)) era `data.lessons` filtrado, sem
`sort`. A ordem do array era o histórico de montagem, e cada aparelho monta
diferente:

- `saveLesson` faz `[lesson, ...current.lessons]` → aula local entra no **topo**.
- `applyFieldPatch` (sync-engine) devolve `[...map.values()]` → aula que chega
  por ação entra no **fim**.
- `mergeBackupData` faz `lessons.push(...)` → idem.

Com `classLessons.slice(0, 8)` em Registros, dois aparelhos com dados idênticos
cortavam aulas diferentes. Parte do "tablet ≠ PC" era isso, não perda de dado.

### Fix
`compareLessonsNewestFirst` em `sync-engine.js`, aplicado **dentro de
`migrateData`** ([main.jsx:427](src/main.jsx)) — ponto único por onde passa
tudo que entra no app (`loadData`, `applyPatch`, `mergeBackupData`,
importação). Ordem: `date` desc → `createdAt` desc → `id` asc.

O desempate por `id` não é decoração: sem ele, duas aulas do mesmo dia sem
`createdAt` ficavam na ordem que cada aparelho por acaso tinha.

Efeito colateral bom: `stableStringify` de array é sensível a ordem, então o
hash de integridade dos dois aparelhos passa a convergir com mais frequência —
menos entradas no ramo de merge de `loadLatestFromSupabase`.

⚠️ A aba "Diário" da planilha (`data.lessons` cru, [main.jsx:4940](src/main.jsx))
herdaria a ordem decrescente. Para planilha a leitura esperada é cronológica,
então ali há um `.slice().reverse()` explícito. Se a ordem canônica mudar, esse
`reverse` mente.

## 2) Causa raiz do item 3: `mergeBackupData` só sabia ADICIONAR

O ramo de aula já existente era literalmente só isto:

```js
const existingStudents = new Set(targetLesson.attendance.map((r) => r.studentId));
for (const record of remappedAttendance) {
  if (!existingStudents.has(record.studentId)) {
    targetLesson.attendance.push(record);
    attendanceRecordsMerged += 1;
  }
}
```

`content`, `periods`, `date` nunca eram atualizados, e status de aluno já
presente nunca era trocado. Nota preenchida × nota preenchida sempre ficava com
o aparelho local (`mergeGradeValueDetailed`, ramo `conflict`).

### Por que isso apagava dado no SERVIDOR, não só na tela

`compactToSnapshot` ([main.jsx:2746](src/main.jsx)):

```
merged = mergeBackupData(dataRef.current, reconstructedRemote).data   // local vence
saveRemoteState(userId, payload)                                       // grava merged
deleteActions(userId, pending.map(r => r.id))                          // APAGA as acoes
```

Linha do tempo que destrói a correção:

```
tablet   edita aula-1: content "A" -> "B", aluno x present -> absent
tablet   acao P sobe pro servidor
PC       compactToSnapshot: reconstroi remoto com P (aula-1 = "B"/absent)
PC       mergeBackupData(local, remoto) -> aula-1 ja existe -> mantem "A"/present
PC       grava "A"/present em diario_current
PC       deleteActions([P])        <- a correcao do tablet deixa de existir
```

O mesmo vale para o ramo de merge de `loadLatestFromSupabase`, que também grava
com `forceSnapshot: true` e chama `deleteActions(appliedActionIds)`.

### Fix: regra de recência, em funções puras

Novas exportações em `src/sync-engine.js` (testáveis em node, seguindo a
decisão de 02/08 de tirar o motor de sync do componente React):

- `recordStamp(item)` → `updatedAt ?? createdAt`, via `toTime` (null se inválido).
- `incomingIsNewer(current, incoming)` → estrito. Empate ou carimbo ausente do
  lado que chega ⇒ `false` (mantém a tela).
- `mergeAttendance(currentList, incomingList, incomingWins)` → união por
  `studentId`, sem mutar as listas recebidas. Devolve `{ attendance, added, updated }`.
- `mergeLessonPair(current, incoming)` → resolve `LESSON_SCALAR_FIELDS`
  (`date`, `periodId`, `periods`, `content`) + chamada. Devolve
  `{ lesson, fieldsUpdated, attendanceAdded, attendanceUpdated }`.

`mergeGradeValueDetailed` ganhou 3º parâmetro `incomingWins` (default `false` =
comportamento antigo). Ligado nos 2 call sites de avaliação e no de
recuperação, com `incomingIsNewer(target, imported)`.

Os carimbos já existiam e não eram usados: `updatedAt` é gravado em
`saveLesson` (edição), `updateGrade` ([main.jsx:4592](src/main.jsx)), edição de
avaliação e recuperação.

⚠️ Quando o lado que chega vence, o `updatedAt` dele **tem que ser copiado
junto** (aula, avaliação e recuperação fazem isso). Sem copiar, o próximo merge
compara contra o carimbo velho e desfaz a atualização que acabou de aplicar.

⚠️ `LESSON_SCALAR_FIELDS` **não** inclui `id` nem `className`: `className` é
resolvido pelo `classIdMap` de quem chama, e o casamento por fallback
(classId+date+periods+content) pode parear aulas com ids diferentes — copiar
`id` ali trocaria a identidade da aula.

⚠️ `Object.assign(targetLesson, resolved.lesson)` é intencional: `targetLesson`
é elemento do array `lessons` já copiado no topo da função, e o resto do laço
continua achando a mesma referência.

## 3) Decisão de projeto: status real ganha de "não chamada", ANTES da data

Em `mergeAttendance` a ordem de precedência é:

1. aluno que só existe de um lado → entra (nunca perde aluno);
2. status real (`present`/`absent`/`excused`) ganha de `not-taken`, **mesmo com
   o carimbo contra**;
3. só entre dois status reais é que `incomingWins` decide.

Motivo de (2) vir antes de (3): o carimbo é da **aula inteira**, não por aluno.
Sem essa precedência, editar o conteúdo de uma aula num aparelho que nunca
recebeu a chamada bastaria para apagar faltas já lançadas no outro.

Custo aceito e comunicado ao usuário: existe botão "Não chamada" por aluno
([main.jsx:6990](src/main.jsx)), e marcar de volta "Não chamada" num aparelho
**não** apaga a chamada no outro. Assimetria deliberada — perder falta é
estrago em documento oficial, sobrar chamada é visível e refazível.

Se um dia houver carimbo por registro de chamada, (2) pode cair e (3) resolve
tudo. É a evolução natural.
