## 1) Causa raiz: service worker cache-first em TODAS as requisições GET
`public/sw.js` (v11) tinha um handler de `fetch` assim:

```js
event.respondWith(
  caches.match(event.request).then((cached) => {
    if (cached) return cached;
    return fetch(event.request).then((response) => {
      const copy = response.clone();
      caches.open(CACHE_NAME).then((cache) => cache.put(event.request, copy));
      return response;
    });
  })
);
```

Sem nenhum filtro de origem. Consequências:

- **Escrita funcionava.** `appendAction` usa `POST` (fetch cru com
  `keepalive:true`) e `saveCurrentState` usa `POST`/upsert via SDK — o handler
  ignora tudo que não é `GET` (`if (event.request.method !== "GET") return;`).
  Por isso o pill "Tudo salvo" estava correto e os dados **foram gravados** no
  Supabase.
- **Leitura ficava congelada pra sempre.** `fetchCurrentState`,
  `fetchPendingActions`, `fetchLatestSnapshots` e `fetchSnapshotById` são todos
  `GET` via PostgREST. Na primeira leitura a resposta ia pro Cache Storage;
  daí em diante `caches.match` acertava e devolvia a **mesma cópia** em toda
  reabertura do app.
- As URLs do app são determinísticas (mesmo `userId`, mesmo `select`), então
  batia sempre a mesma entrada de cache. Pior: o `sinceIso` de
  `fetchPendingActions(userId, current.updated_at)` vinha do `updated_at`
  **cacheado**, então até a URL das ações pendentes era idêntica toda vez —
  o caminho de leitura inteiro ficava travado no tempo.

**Por que só apareceu agora**: até `fe7a59e` (20/07) o `sw.js` estava na raiz
do projeto e o Vite não copiava pro build — dava 404 em produção e o service
worker **nunca rodava**. O commit que "consertou" a instalação como app foi
exatamente o que colocou o bug no ar. Relato do usuário 9 dias depois.

### Fix
Reescrito `public/sw.js` (v12, `CACHE_NAME = "meu-diario-v12"`):
- `if (url.origin !== self.location.origin) return;` — qualquer coisa fora do
  próprio site (Supabase inclusive) passa direto pra rede, sem cache. **Esta é
  a linha que corrige a perda de dados.**
- Navegação (`event.request.mode === "navigate"`) virou **network-first** com
  cache só como reserva offline. Antes era cache-first, o que significava que
  uma versão nova do app **nunca chegava** em quem já tinha instalado — o
  `index.html` ficava preso no cache indefinidamente.
- Estáticos do build continuam cache-first (o Vite põe hash no nome, conteúdo
  nunca muda pro mesmo nome), mas só gravam se `response.ok && response.type
  === "basic"`.
- O bump de `CACHE_NAME` é o que **limpa as respostas do Supabase envenenadas**
  nas máquinas já instaladas: o handler de `activate` apaga todo cache com
  nome diferente do atual.

### Recuperação nas máquinas afetadas
Não precisa de ação manual: o navegador checa `/sw.js` na rede a cada navegação
(a requisição do próprio script do SW não passa pelo handler de `fetch` dele),
instala a v12, `skipWaiting` + `clients.claim`, e o `activate` apaga o cache
v11. **Precisa recarregar duas vezes**: a primeira troca o service worker, a
segunda já busca `index.html` da rede.
⚠️ **Não** orientar "Limpar dados do site" no Chrome — isso apagaria também o
`localStorage`, que guarda a cópia local do diário. Se precisar forçar na mão:
F12 → Application → Service Workers → Unregister, e apagar só o cache
`meu-diario-v11` em Cache Storage.

## 2) Bug irmão: ações pendentes descartadas quando não há snapshot
`loadRemoteState` (`src/main.jsx`, ~linha 570) começava assim:

```js
const current = await fetchCurrentState(userId);
if (!current?.payload) return null;   // <- aborta antes de olhar as ações
```

Se ainda não existe linha em `diario_current` (professor novo, ou a primeira
`compactToSnapshot()` falhou — ela é chamada sem `await` com
`.catch(console.warn)`, então falha **em silêncio**), todas as edições vivem só
em `diario_actions` e eram **completamente ignoradas** no carregamento. O app
mostrava diário vazio com tudo gravado no servidor.

**Fix**: busca as ações pendentes mesmo sem `current`, e reconstrói a partir de
`initialData`:

```js
const pending = await fetchPendingActions(userId, current?.payload ? current.updated_at : undefined);
if (pending.length) {
  const base = migrateData(current?.payload?.data ?? initialData);
  return { ...(current?.payload ?? {}), data: applyPatches(base, pending) };
}
return current?.payload ?? null;
```

Sem `current`, chama `fetchPendingActions` **sem filtro de data** (mesma lógica
já usada em `compactToSnapshot` — ver seção 5 do rastreio de 19/07 sobre ações
órfãs). Professor novo de verdade (sem snapshot e sem ações) continua caindo em
`return null`, comportamento inalterado.

## 3) Teste de regressão novo
`scripts/sw-safety.test.mjs` — carrega o `public/sw.js` **de verdade** (não uma
cópia) num escopo falso de service worker via `node:vm`, e dispara eventos de
`fetch` sintéticos checando apenas se `respondWith` foi chamado ou não:

- GET em `diario_current` / `diario_actions` de outro domínio → **não** pode ser
  respondido pelo SW;
- POST em `diario_actions` → **não** pode ser respondido;
- navegação e estáticos do próprio site → **devem** continuar sendo respondidos
  (suporte offline preservado);
- `hostname = localhost` → SW sai da frente por completo.

**Validado que o teste presta**: rodado contra o `sw.js` antigo
(`git checkout public/sw.js`), falha na primeira asserção com
`true !== false`. Restaurado e passa. Sem essa verificação o teste não teria
valor nenhum.

`package.json`: adicionados `test:sw` e um `test` agregado
(`npm run test:sync && npm run test:sw`).

## Armadilhas técnicas para sessões futuras (LLM ou humano)
- **Herdadas do rastreio de 19/07 e ainda válidas**: nunca usar pipes de texto
  cru do PowerShell em arquivos com acentuação (usar `Edit`); HMR duplica
  montagem se `build` roda junto com `start`; motor de diff é idempotente por
  `id`; `diario_actions` deve ser varrida sem filtro de data na compactação;
  sem chave `service_role` disponível pro Claude (SQL é manual no painel).
  Correção: `git` **está** disponível no PATH do Bash nesta sessão — o aviso
  antigo sobre precisar do binário do GitHub Desktop não se aplicou aqui.
- **Service worker é caminho crítico de dados neste app.** Qualquer mexida em
  `public/sw.js` tem que rodar `npm run test:sw`. A regra é: o SW só toca em
  arquivos do próprio site, nunca em chamada de rede pro servidor de dados.
- **`IS_LOCAL_DEV` desliga o SW em `localhost`** — ou seja, comportamento de
  service worker **não é testável** com `npm run start` nem `vite preview`
  (ambos servem em localhost). Por isso o teste em `node:vm` existe: é a única
  verificação automatizável de SW neste projeto.
- **Cache-first em `navigate` prende o app numa versão pra sempre.** Se um dia
  alguém reclamar que "a atualização não chegou", olhar o SW primeiro.
- **`compactToSnapshot()` falha em silêncio** quando disparada pelo caminho
  automático (`appendActionToSupabase` chama sem `await`, com
  `.catch(console.warn)`). Não foi mexido nesta sessão, mas é a razão de o
  cenário "sem linha em `diario_current`" ser alcançável na prática.
